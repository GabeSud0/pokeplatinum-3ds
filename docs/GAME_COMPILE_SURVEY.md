# Platinum GCC game-source compilation survey

The native 3DS port builds an initial subset of original game C files as
`libplatinum_game.a`. That is necessary, but it does not show how close the
remaining original sources are to building. The diagnostic survey measures
**actual GCC frontend compilation failures** across a deterministic, broad
sample of the pinned `pret/pokeplatinum/src/` checkout.

It does not compile game assets, produce ROM content, link executables, modify
Nintendo sources, or assume a playable game. It uses the same compiler,
SDK include paths, 107 Metang headers, original game PCH, and baseline C
compiler flags as the real game build, plus explicitly documented diagnostic-
only platform selectors for the original GameSpy headers.

## Run

After `python tools/bootstrap.py --clean` (and with your normal SDK build
prerequisites available), run:

```sh
make -C 3ds_port/game TARGET=host probe
make -C 3ds_port/game TARGET=host32 probe
make -C 3ds_port/game TARGET=3ds probe

# Investigate all original C sources rather than the bounded CI sample:
make -C 3ds_port/game TARGET=host probe PROBE_LIMIT=0

# Smaller diagnostic sample:
make -C 3ds_port/game TARGET=3ds probe PROBE_LIMIT=20
```

By default, the tool samples 64 source files. It hashes each filename
**relative to the upstream `src/` directory** and uses the first N
SHA-256-ranked paths, then sorts those selected files. A sample therefore
spans subsystems instead of sampling only the beginning of the alphabet;
the same pinned upstream revision and limit select the same files on
different machines. `PROBE_LIMIT=0` requests the entire source tree.

## Original build dependencies now supplied

The first survey exposed `spl.h` and
`res/pokemon/regional_pokedex_size.h` as common missing headers.

- `spl.h` already exists in the pinned upstream game checkout at
  `lib/spl/include/`. The GCC game build now includes that original
  directory; this **does not yet compile or implement the SPL runtime**.
  Particle drawing, updating, VRAM and geometry backends still need work.
- `regional_pokedex_size.h` is generated by upstream's `dexproc` from
  `res/pokemon/sinnoh_pokedex.json`. For the GCC port,
  `tools/prepare_game_resource_headers.py` reproduces precisely
  the header's metadata definition `REGIONAL_DEX_COUNT = len(list) - 1`.
  The pinned 211-entry list yields 210. This generator does not package
  the Pokédex NARC files or extract any game assets.

The generated header lives under ignored
`build/game-resource-headers/res/pokemon/`. Both inputs are tracked as
Makefile dependencies and are available for the host, host32 and devkitARM
compiler surveys. Source files that now pass **syntax** may still have
unresolved linker/runtime dependencies.

### Original Wi-Fi SDK headers (compile survey only)

The upstream game includes `dwc.h` through `wifi_list.h`. It isn't
part of NitroSDK or NitroSystem: the pinned game build declares separate
`NitroDWC` and `NitroWiFi` dependencies, recorded as full Git SHA-1s in
`subprojects/NitroDWC.wrap` and `subprojects/NitroWiFi.wrap`.

`tools/prepare_game_network_headers.py` fetches both exact upstream
revisions, verifies the SHA and repository origin, and makes their original
headers available under ignored `build/game-network-sdks/`. Run:

```sh
python tools/prepare_game_network_headers.py
make -C 3ds_port/game TARGET=host probe PROBE_LIMIT=80
```

The Makefile's `probe` target prepares those headers automatically. The
already-passing 16-file game library and host tests do **not** need to
fetch the networking SDKs. The original `include`, `include/gs`, and
`include/base` directories are added to GCC's header search path.

The next diagnostic blocker was GameSpy's `include/gs/nonport.h`, whose
platform selection requires an original platform macro. The **survey alone**
now uses its documented upstream branches: `-D_LINUX` on host/host32
(Unix/POSIX socket declarations) and `-D_NITRO` for devkitARM (Nintendo DS
declarations). Those macros are deliberately **not** added to normal game
compilation. An error after selecting the Nintendo branch—for example a
separate unavailable `extras.h` or a platform-dependent DS function—is
a genuine subsequent dependency, not license to create fake networking APIs.
Also, the Unix branch can pass frontend syntax without working under a 3DS
runtime. Compare the **same** sample sizes before and after.

This is **header and type discovery only**, NOT Nintendo WFC emulation,
connection support, runtime behavior, or linked NitroDWC/NitroWiFi libraries.
Compiling sources may now reveal additional authentic missing APIs/types;
do not fabricate definitions to silence them.

### Source-derived text-bank message indices

The original `tools/msgenc/Json.cpp::WriteHeader` generates C macros for
each message's `id` using its **position in the JSON messages array**,
starting at zero, and also generates a `TEXT_BANK_<NAME>_ENTRY_COUNT`
macro. These identifiers and indices do **not** depend on the encrypted
message text or the final compiled `pl_msg.narc`.

`tools/prepare_game_text_bank_headers.py` reproduces only this ID metadata
from the existing static `res/text/*.json` files in the **pinned** upstream
checkout. The Makefile now runs it before compiling the existing game slice
and before compiler surveys. It produces headers at
`build/game-resource-headers/res/text/bank/*.h`. The generated headers
contain no text, dialogue, keys or archive data. No ROM dump is required.

The original `tools/dataproc/src/moveproc.c::proc_text` supplies four
additional dynamic message banks. It walks `generated/moves.txt` in enum
order, loads the corresponding `res/moves/<stem>/data.json`, then creates
one name, uppercase name and description ID per move plus three
ally/wild/foe IDs in `moves_used_in_battle`. The game GCC build now
runs `tools/prepare_game_move_text_headers.py`, which checks every
corresponding source record and recreates **only those four C ID headers**.
For the pinned revision, that is 468 moves; the three ordinary banks
have 468 entries each and `moves_used_in_battle` has 1,404 entries.
No actual names, descriptions or battle dialogue are emitted. The
headers are located in the same ignored resource metadata directory.

The original `tools/dataproc/src/speciesproc.c::emit_textbanks` also
creates `species_name` and `species_name_with_articles` in the
`generated/species.txt` enum order, from `SPECIES_NONE` through
`SPECIES_BAD_EGG`. `tools/prepare_game_species_text_headers.py`
reproduces only those two banks' message IDs after validating the
corresponding `res/pokemon/<species>/data.json` records. The pinned
revision contains **496 original species slots**, including the reserved
None/Egg/Bad Egg slots. Alternate-form data processed after BAD_EGG does
not add names to these banks. The generated headers include **only macros
and entry counts**, not Pokémon names, Pokedex text or assets.

Other dynamic/generated banks—such as species Pokédex descriptions,
trainer names and item descriptions—still require their original
underlying data processing. Even when an ID header is available,
the actual message NARC and associated rendering/loading system are
**not** built.

### Original NitroSFX sound index metadata

The original `tools/nitrosfx/sdat.c::WriteNaix` generates
`res/sound/pl_sound_data.naix` from the ordered `pl_sound_data.json`
metadata using the `-naix` option. Each nonempty record has an index
**within its own SDAT info array**. NitroSFX uses the resource `fileName`
for sequences, banks and wave archives; player and group categories use
`name`. Duplicate filenames in a category acquire numeric suffixes;
empty names leave reserved index slots.

`tools/prepare_game_sound_naix.py` reproduces just those macro
definitions from the pinned manifest, generating an ignored
`build/game-resource-headers/res/sound/pl_sound_data.naix` before
game compilation and compiler surveys. It does not create `.sdat`,
`.sseq`, `.sbnk`, `.swar` or audio content and does not imply
a working sound engine. The game library remains a partial archive.

### Source-derived NitroArc graphics member indices

The upstream graphics builds invoke `nitroarc --create --index --files-from
<archive>.order`. The original NitroArc `write_index` emits a macro for
each explicitly listed archive member at its original **zero-based position**,
substituting underscores for path separators, periods and punctuation.
Repeated identical names gain suffixes `_1`, `_2` and so on.

`tools/prepare_game_graphics_naix.py` reproduces **only these explicit
member-index definitions** from the pinned `res/graphics/**/*.order`
manifests, under ignored `build/game-resource-headers/res/graphics/`.
It works without loading source artwork, generating texture resources, or
building `.narc` files. It runs before the real game compilation and
all compiler surveys. We test known first indices from Pokétch and
Battle Frontier source manifests.

NitroArc can append implicit files found in its *generated input directory*.
Those files are not available from the ordered manifest alone; therefore
the metadata-only generator **does not emit any full-archive COUNT macro**
or claim to provide indices for such implicit members. Their actual
archive indices, resource bytes, and on-hardware behavior require the
original NitroArc asset-processing pipeline. This is only a compiler
dependency improvement, not graphics implementation.

For graphics metadata generation:
```sh
python tools/prepare_game_graphics_naix.py --upstream build/upstream --output build/game-resource-headers
```

Reports are written to:

```text
build/game-compile-survey/host.json
build/game-compile-survey/host32.json
build/game-compile-survey/3ds.json
```

All reports are under ignored `build/`; nothing fetched or generated
belongs in the source repository. CI uploads JSON reports as Actions
artifacts for review. Each record includes the original source's relative
path, compilation category, timing, and first compiler error.

## Understanding the results

| Status | Meaning |
|---|---|
| `passed` | GCC accepted this translation unit with `-fsyntax-only` |
| `missing_generated_header` | Header is not yet generated by the build |
| `missing_resource_header` | Original source includes a game resource header not yet prepared |
| `missing_header` | Other dependency missing from the compilation include paths |
| `unsupported_gamespy_platform` | Original GameSpy header rejects its selected platform; inspect the target macro |\n| `type_or_symbol` | A type, field or declaration mismatch/undefined name |
| `compiler_error` | Other syntax or GCC compatibility error |
| `timeout` | Compiler did not finish within the configured per-file limit |
| `compiler_unavailable` | Toolchain could not be launched |

Surveys are **non-gating by design**: finding failed files is their purpose.
They print a summary and preserve failures in JSON, while the existing
`libplatinum_game.a` build and tests remain **required** in CI. To fail
for any compiler diagnostic, invoke the Python tool with `--strict`.
Successful syntax-only compilation is **not** a link test, runtime test,
asset validation, or demonstration that overlays can boot.

## Next steps

1. Compare host/host32/3DS JSON reports, starting with missing generated
   resource headers and recurring type errors.
2. Group repeatable failures by subsystem. Fix build plumbing centrally
   where possible instead of adding permissive stubs.
3. When changing original decompilation C, use a focused
   `patches/pokeplatinum/*.patch` with `SDK_PORT_3DS` guards, as required
   by `CONTRIBUTING.md`.
4. Move a cohesive new set of files into `GAME_SRCS` only after they
   compile for the target and are covered by meaningful host tests.
5. Maintain a separate plan for overlays, game entry point, filesystem,
   graphics, audio and the eventual Azahar title-screen milestone.

Game content remains in the player's own legally dumped ROM and is never
committed to this repository.
